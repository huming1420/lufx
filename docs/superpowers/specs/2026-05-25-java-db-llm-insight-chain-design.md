# Java Database-Backed LLM Insight Chain Design

## 1. Objective

Implement the Java production path for dashboard insights so that:

- Business metric facts are loaded from PostgreSQL tables, not supplied by the browser and not read from a JSON resource during normal requests.
- The existing `dashboard_metrics_mock.json` and `card_config.json` files are imported once as clearly labelled demo seed data so the application is runnable before real source data is connected.
- Card traffic lights and analysis tags are generated by the LLM from metric facts and thresholds.
- The operating calculator receives LLM-generated default analyses for pessimistic, baseline, and optimistic scenarios based on the stored snapshot.
- The existing HTML pages receive data through compatible Java API endpoints and display stored/LLM-generated results.

This design uses the Python backend only as a behavioral reference. Runtime implementation is Java and PostgreSQL only.

## 2. Current State And Constraints

The current Java service has `insight_result`, `insight_job`, and `insight_job_item` persistence, but no database tables for business facts. `InsightService` currently consumes request-supplied `input_data`, while `/api/dashboard/mock` reads `dashboard_metrics_mock.json` directly. The HTML pages call `/api/insights/*` routes that are not fully represented in the current Java controllers.

The seed JSON contains existing `status` values. These are not authoritative AI output under the new requirement. They may be retained only as source-reference fields for traceability, and must not be used to render card traffic lights or as an instruction forcing the LLM's card conclusion.

The initial snapshot is demo content:

- `source_type`: `DEMO_SEED`
- `source_label`: `演示数据，待替换`

Responses that use this snapshot must expose this labelling.

## 3. Chosen Architecture

### 3.1 Persistence Model

Add tables for stored facts and bindings:

#### `metric_snapshot`

Stores snapshot metadata.

| Column | Purpose |
| --- | --- |
| `period` | Business period, primary lookup dimension |
| `metric_version` | Hash/version of imported source facts |
| `source_type` | `DEMO_SEED` initially, later a real import source |
| `source_label` | Human-readable provenance label |
| `source_file` | Seed/import origin when applicable |
| `imported_at` | Import timestamp |

For a requested period, the active snapshot is the record with the greatest `imported_at`, breaking ties by descending primary key. An explicit `metric_version` may be supplied by administrative/debug paths only; normal UI requests use the active snapshot.

#### `business_metric`

Stores core and segmented metric facts for a snapshot.

| Column group | Fields |
| --- | --- |
| Identity | `period`, `metric_version`, `metric_scope`, `metric_code`, `dimension_key` |
| Description | `metric_name`, `module`, `dimension`, `segment`, `unit` |
| Values | `value`, `yoy`, `mom`, `budget`, `budget_gap` |
| Display facts | `display_value`, `display_yoy`, `display_budget_gap`, `display_distance_to_redline` |
| Threshold facts | `redline`, `yellowline`, `distance_to_redline`, `direction` |
| Trace-only source value | `source_status` |
| Extended dimensions | `product_type`, `channel_type`, `customer_type`, `vintage`, `mob` |

`source_status` records what the imported demo file contained, but card LLM fact packs exclude it as a conclusion. Threshold facts and raw values remain available to the LLM as evidence.

#### `card_definition`

Stores card identity, display title, module, hierarchy/view metadata, and prompt/schema version.

#### `card_metric_binding`

Maps a card to business metric codes so the Java service can query a card fact pack without resource-file lookup.

#### `scenario_baseline`

Stores the three default calculator scenarios and their input parameters for each snapshot:

- `bear`: pessimistic
- `base`: baseline
- `bull`: optimistic

Parameters include ANR, consumer finance growth, pricing rate, credit loss rate, NPL rate, funding cost rate, sales cost rate, operating cost rate, tax/other rate, and non-loan profit where available.

### 3.2 Existing Insight Persistence

Extend `insight_result` to retain analysis provenance and front-end response material:

- `schema_name`
- `title`
- `standard_insight`
- `drivers_json`
- `watch_items_json`
- `analysis_labels_json`
- `traffic_light`
- `scenario_exploration_json`
- `raw_fact_pack_json`
- `raw_llm_output_json`
- `validation_error`

Caching remains partitioned by `period`, `metric_version`, `prompt_version`, `insight_type`, and `card_id`. A change to facts creates a new `metric_version`, so stale LLM conclusions are not returned as current.

`insight_result.status` is generation lifecycle state (`pending`, `running`, `ready`, or `failed`). It must never represent red/yellow/green business assessment; business assessment is stored in `traffic_light`.

## 4. Seed Import And Future Replacement

Introduce a Java seed/import service invoked on startup:

1. Check whether a `DEMO_SEED` snapshot for the JSON period/version already exists.
2. If absent, parse classpath `data/dashboard_metrics_mock.json` and `data/card_config.json`.
3. Insert snapshot metadata, core/segment metrics, card definitions, card bindings, and three scenario defaults in a transaction.
4. Do not overwrite an existing snapshot on every restart.

Normal request handling never reads the JSON files for metrics. It uses repositories over the new tables.

The future real-data replacement path is deliberate: an import job or upstream integration can write a new `metric_snapshot` and associated `business_metric` / `scenario_baseline` records using a source type other than `DEMO_SEED`. No LLM or UI contract needs to change.

## 5. Fact Pack Construction

Add a repository-backed fact-pack service. It accepts `period` and optional `card_id` or `scenario_id`, resolves the latest snapshot for the period, and builds JSON structures for LLM calls.

### 5.1 Card Fact Pack

Each card fact pack contains:

- Data source metadata and snapshot version.
- Card identity and associated metric codes.
- Raw metric values, trend values, budget comparison, threshold values, and direction.
- Segment metric facts where configured.
- Derived evidence strings only when directly traceable to stored facts.

It must not contain `traffic_light`, AI labels, or an authoritative prefilled `status`. The imported `source_status` is excluded from the LLM instruction payload.

### 5.2 Dashboard Fact Pack

The dashboard fact pack contains all stored core facts, dimensions/modules, threshold facts, data-source metadata, and available cross-metric context. Dashboard health labels and narrative are LLM outputs.

### 5.3 Scenario Fact Pack

For `bear`, `base`, and `bull`, the service loads scenario input parameters from `scenario_baseline`, supplies relevant current metric facts as benchmark context, computes only transparent numeric calculator results where required for display, and sends inputs plus computed results to the LLM for interpretation.

The LLM does not invent source measurements; it interprets stored facts and declared scenario inputs.

## 6. LLM Output Contracts

Update prompt templates and JSON schemas so LLM output is explicit and validated.

### 6.1 Card Output

Required fields:

- `card_id`
- `traffic_light`: `red`, `yellow`, or `green`
- `analysis_labels`: array of short tags generated from evidence
- `standard_insight`
- `drivers`: array
- `watch_items`: array
- `evidence`: array referring to facts in the fact pack

The prompt states:

- Determine traffic light and tags from raw facts, thresholds, direction, trends, and budget gaps.
- Do not assume a pre-calculated traffic-light conclusion.
- Do not add unsupported values.

### 6.2 Dashboard Output

Required fields include:

- `health_label`
- `overall_traffic_light`
- `standard_diagnosis`
- `dimensions`
- `root_causes`
- `offset_factors`
- `management_questions`

### 6.3 Scenario Output

Required fields include:

- `scenario`
- `scenario_label`
- `inputs`
- `computed`
- `standard_explanation`
- `scenario_exploration`
- `traffic_light`
- `analysis_labels`

The three default scenarios use the same output contract and are cached independently.

## 7. Service And API Flow

### 7.1 Initial Page Data

Implement Java-compatible endpoints used by the current pages:

- `GET /api/dashboard/data`: returns snapshot facts, card definitions, scenario defaults, and source labelling.
- `GET /api/insights/page-state?period=...`: returns card-generation states and cached card output.
- `GET /api/insights/dashboard?period=...`: returns cached or running/missing dashboard insight state.
- `POST /api/insights/jobs`: creates generation jobs for dashboard/cards/default scenarios.
- `GET /api/insights/jobs/{jobId}`: returns job progress/results.
- `POST /api/insights/scenario`: returns cached or newly generated scenario analysis for default/custom calculator input.

Legacy Java endpoints may delegate to the same services, but `/api/insights/*` is the UI-facing contract.

### 7.2 Card Generation

1. Resolve snapshot from the database.
2. Query card and associated metric facts.
3. Build fact pack and metric-version cache key.
4. Call LLM unless a valid cached result exists or refresh is requested.
5. Validate response, store raw fact pack and raw/output JSON.
6. Return AI traffic light, labels, narrative, drivers, watch items, and source labelling.

### 7.3 Scenario Defaults

During an `all` or scenario-initialization generation job:

1. Load `bear`, `base`, and `bull` parameters from `scenario_baseline`.
2. Build three scenario fact packs from the same snapshot.
3. Generate and cache each LLM result independently.
4. Expose the three results to the calculator so its initial scenario buttons, values, and interpretation are backed by database-loaded demo facts and LLM output.

User-edited slider values form a custom scenario request and produce a separate cached LLM result using a parameter hash.

## 8. Front-End Behavior

### `lufax_dashboard3.html`

- Replace hardcoded card status presentation with API-loaded `traffic_light`.
- Replace static analysis tags with `analysis_labels`.
- Continue to display waiting/running/failed states explicitly while generation is incomplete.
- Display `演示数据，待替换` when the current snapshot source is `DEMO_SEED`.

### `ai_insights.html`

- Load dashboard health result and default scenario analyses from Java APIs.
- Replace hardcoded calculator `SCENARIOS` initial values once API results are loaded.
- Keep the slider interaction, but submit edited inputs for a custom AI scenario explanation.
- Surface source labelling and avoid presenting demo data as current production truth.

## 9. Error Handling And Fallbacks

- Missing snapshot: API returns an explicit missing-data status; no invented analysis is shown.
- LLM error or invalid JSON: store failed result with validation error, return failed state, and preserve prior result only as clearly marked stale fallback if available.
- Seed import failure: fail application startup or expose unhealthy state rather than silently serving hardcoded pages as live data.
- Demo source: always return data source metadata to the UI.

No fallback may fabricate red/green/yellow results in place of a failed AI call.

## 10. Testing And Validation

Implementation will follow test-first changes.

### Repository And Seed Tests

- Create new tables in H2 test schema.
- Import demo resource records idempotently.
- Query snapshot, card bindings, metrics, and all three scenario baselines.

### Fact Pack Tests

- Card pack contains stored numeric facts and thresholds.
- Card pack excludes imported `source_status` as a model conclusion.
- Dashboard/scenario packs contain provenance metadata and source facts.

### Insight Service Tests

- LLM-returned traffic light and labels persist and round-trip in card API results.
- Invalid LLM response results in failed status, not a local traffic-light guess.
- Scenario `bear`, `base`, and `bull` each create LLM-backed cached results.

### API Tests

- `/api/dashboard/data` reads database-backed demo snapshot and reports `DEMO_SEED`.
- `/api/insights/page-state`, `/dashboard`, `/jobs`, and `/scenario` satisfy front-end response contracts.

### Browser Validation

- Run the Java service locally.
- Open both HTML pages using the local server.
- Verify card lights/tags are populated from API responses.
- Verify the calculator loads the three default AI-backed scenarios and handles a custom update.
- Verify the demo-data label remains visible.

## 11. Non-Goals

- Connecting an undisclosed production data source in this increment.
- Treating the seed JSON values as real-time production facts.
- Letting client-provided arbitrary `input_data` replace the stored snapshot in standard dashboard/card generation.
- Retaining hardcoded front-end status or analysis content as authoritative output once the API path is active.
